# 云端市场当前完成度评估

本文档基于当前代码实现整理，用于判断 AnyClaw 云端市场目前已经完成的能力、仍不完善的地方，以及后续进入服务器配置和官网建设前的推进建议。

## 总体结论

当前云端市场已经完成了 MVP 主闭环，约等于完成了核心能力的 70%。

已经具备：

- 云端 registry 服务
- AnyClaw 客户端连接云端市场
- 本地市场和云端市场目录
- Agent / Skill / CLI 条目浏览
- 云端 artifact 安装
- 安装进度和 job 状态
- 安装安全策略
- 绑定、升级、卸载
- Agent 通过工具搜索市场能力
- 官网读取 registry 数据的基础入口

还未达到完整生产级市场状态，主要缺口在：

- 智能搜索和能力发现
- 完整发布后台
- 官网产品化展示
- 安装后自动集成体验
- 更强的安全体系
- 生产级云端部署架构

## 已经实现的功能

### 1. 本地市场目录

本地市场已经能展示本机可见的能力目录，包括：

- 本地 agent profiles
- 本地 agent store 条目
- 本地 skills catalog
- CLIHub 条目

当前支持的本地类型：

- `agent`
- `skill`
- `cli`
- 后端也支持 `plugin`，但当前 UI 没有开放 plugin 类型入口

本地市场不是简单等于“全部已经安装”，而是“本机可见的能力目录”。其中可能包含：

- `installed`：已安装
- `active`：当前激活
- `bound`：已绑定
- `disabled`：已禁用
- `available`：本地目录中可用但未安装或未启用

### 2. 云端市场目录

项目中已经实现独立 registry 服务：`anyclaw-registry`。

主要接口包括：

```text
GET  /v1/health
GET  /v1/control-plane
GET  /v1/sources
GET  /v1/artifacts
GET  /v1/artifacts/{id}
GET  /v1/artifacts/{id}/versions
POST /v1/artifacts/{id}/resolve
GET  /v1/download/{artifact_id}/{version}
POST /v1/search
POST /v1/publish
POST /v1/artifacts/{id}/quarantine
POST /v1/artifacts/{id}/unquarantine
GET  /v1/admin/audit
GET  /v1/admin/downloads
```

这说明云端市场后端不是空壳，已经具备真实 registry 能力。

### 3. AnyClaw 客户端连接云端市场

AnyClaw 客户端可以通过配置连接云端 registry。

相关配置字段包括：

```json
{
  "marketplace": {
    "registry_endpoint": "http://your-server:8791",
    "registry_token": "",
    "protocol_version": "1.0",
    "disable_remote": false,
    "cache_ttl_seconds": 0,
    "request_timeout_seconds": 30,
    "download_timeout_seconds": 300,
    "retry_count": 0,
    "auto_install_skill": false
  }
}
```

当 `registry_endpoint` 不为空且 `disable_remote=false` 时，客户端可以访问云端市场。

### 4. 市场 UI

当前 UI 已经支持：

- 切换 `Agent / Skill / CLI`
- 切换 `Local / Cloud`
- 搜索市场条目
- 查看 artifact 详情
- 查看权限、风险、信任等级、兼容性、依赖
- 查看版本信息
- 安装云端 artifact
- 绑定 artifact
- 升级 artifact
- 卸载 artifact
- 查看安装进度

安装步骤 UI 展示为：

```text
Resolve
Download
Verify
Install
Receipt
```

### 5. 云端 artifact 安装

当前安装流程已经完整覆盖：

```text
resolve -> download -> verify checksum -> extract -> install -> write receipt
```

安装后的本地数据主要写入：

```text
.anyclaw/marketplace/installed
.anyclaw/marketplace/receipts
.anyclaw/marketplace/jobs
.anyclaw/marketplace/bindings
.anyclaw/marketplace/audit
.anyclaw/marketplace/events
```

安装器支持：

- zip 包
- tar.gz / tgz 包
- checksum 校验
- manifest 校验
- 路径逃逸防护
- symlink 拒绝
- 安装失败回滚

### 6. 安装安全策略

当前已经有基础安装策略。

当满足以下条件时，skill 可以自动安装：

```text
auto_install_skill=true
kind=skill
risk_level=low
trust_level=verified
```

其他情况通常需要用户确认。

如果策略阻止或校验失败，安装会失败并写入 job、audit、event 记录。

### 7. 安装任务和进度

后端已经支持安装任务记录。

主要能力：

- 创建 install job
- 创建 upgrade job
- 查询 job 列表
- 查询 job 详情
- 幂等键复用
- 记录进度步骤
- 记录失败原因
- 记录成功 receipt

相关接口：

```text
GET /market/jobs
GET /market/jobs/{id}
```

### 8. 绑定能力

已安装 artifact 可以绑定到：

```text
main_agent
workspace
runtime_global
persistent_subagent
```

绑定后会写入 binding 记录，并触发 runtime hot reload。

绑定相关接口：

```text
GET    /market/bindings
POST   /market/bindings
DELETE /market/bindings/{id}
```

### 9. 升级能力

当前已经支持 artifact 升级。

升级流程复用安装链路，升级成功后会更新已有 binding 指向新的 receipt/version。

升级失败时，旧 receipt 和旧 binding 会保留。

### 10. 卸载能力

当前已经支持卸载。

卸载会执行：

- 查找 receipt
- 删除相关 bindings
- 删除安装目录
- 删除 receipt
- 写 audit
- 写 event
- 触发 runtime refresh

卸载结果中会包含：

- artifact id
- receipt id
- 删除的 binding id
- 删除路径
- 上一个版本
- 卸载时间

### 11. 云端发布和管理能力

registry 已支持发布 artifact：

```text
POST /v1/publish
```

已有辅助脚本：

```text
scripts/registry-publish-artifact.ps1
scripts/registry-create-publisher-token.ps1
scripts/registry-revoke-publisher-token.ps1
scripts/registry-backup.ps1
scripts/registry-restore.ps1
```

已有部署辅助脚本：

```text
deploy/registry-smoke.ps1
deploy/registry-backup.sh
deploy/registry-restore.sh
```

registry 管理能力包括：

- admin token
- publisher token
- 发布者 token 校验
- artifact quarantine
- artifact unquarantine
- audit events
- download stats
- backup / restore

### 12. Agent 自动搜索市场能力

当前已经注册 Main Agent 专用市场工具：

```text
market_search_artifacts
market_install_artifact
market_bind_artifact
```

这些工具只对 Main Agent 可见，Sub Agent 默认不能调用。

能力搜索流程：

```text
输入 query -> 搜索本地已安装 receipt -> 搜索云端 registry -> capability route 推荐动作
```

推荐动作包括：

```text
use_installed
install_from_market
no_match
```

### 13. 官网读取市场数据

官网目录中已经有 registry client，可以读取：

```text
/v1/artifacts?limit=100
```

说明官网已经有读取云端市场数据的基础能力。

## 当前筛选和搜索机制

### UI 层筛选

当前市场 UI 主要传递：

```text
kind
source
q
limit=100
```

也就是：

```text
/market/artifacts?kind=agent&source=cloud&q=xxx&limit=100
/market/artifacts?kind=skill&source=cloud&q=xxx&limit=100
```

### 本地市场筛选

本地市场支持：

- `kind` 精确匹配
- `source` 精确匹配
- `status` 精确匹配
- `q` 文本包含匹配

本地 `q` 搜索字段包括：

- `id`
- `name`
- `display_name`
- `description`
- `version`
- `owner`
- `category`
- `kind`
- `source`
- `source_id`
- `status`
- `tags`
- `permissions`
- `capabilities`
- `metadata`

本地排序规则：

```text
kind 升序 -> source 升序 -> name 字母序
```

### 云端市场筛选

云端 registry 后端支持：

- `kind`
- `source`
- `q`
- `risk`
- `trust`
- `limit`
- `offset`

但当前 UI 实际主要使用：

- `kind`
- `q`
- `limit`
- `offset`

云端 `q` 搜索字段包括：

- `id`
- `name`
- `summary`
- `description_md`
- `publisher`
- `tags`
- `hit_signals`

云端排序规则：

```text
score 从高到低
score 相同则 updated_at 从新到旧
```

### Agent 能力路由

Agent 自动搜索能力时，会先做基础需求归一化。

示例：

```text
release note / changelog / 发布说明 / 版本说明 -> release notes
code review / pull request / 风险检查 / 代码审查 -> code review
repo health / diagnose repo / 仓库健康 / 诊断 -> repo health
```

然后把需求拆成词，要求每个词都能在 artifact 能力索引中匹配到。

当前匹配字段：

- artifact id
- name
- kind
- capabilities

## 还未实现或不够完善的地方

### 1. 搜索还不是智能语义搜索

当前搜索主要是普通字符串包含匹配，不是 embedding 或语义搜索。

例如用户说“帮我检查 PR 风险”，系统目前主要依赖关键词映射到 `code review`，不是通过语义向量理解需求。

建议后续升级为：

```text
关键词搜索 + 标签搜索 + capability index + embedding 向量搜索 + 综合评分
```

### 2. Agent 自动补能力闭环还不够自然

当前 Agent 已经可以调用市场工具，但体验还偏工具化。

理想闭环应该是：

```text
发现能力不足
-> 判断缺少什么能力
-> 搜索本地和云端市场
-> 解释候选能力
-> 请求用户确认
-> 安装
-> 绑定
-> 热刷新
-> 立即使用新能力
```

当前骨架已经存在，但自然语言触发、候选解释、自动绑定策略、安装后立即使用还需要继续打磨。

### 3. UI 筛选项不足

当前 UI 主要开放：

- 类型
- 来源
- 搜索词

后续应该增加：

- 风险等级
- 信任等级
- 权限
- 标签
- 发布者
- 是否官方认证
- 是否兼容当前系统
- 是否兼容当前 AnyClaw 版本
- 是否已安装
- 是否可升级

### 4. 云端排序和评分仍然简单

当前云端排序主要依赖：

```text
score
updated_at
```

建议后续评分加入：

- 下载量
- 安装量
- 评分
- 安装成功率
- 是否官方认证
- 发布者信任等级
- 风险等级
- 权限敏感度
- 与当前需求的匹配度
- 与当前系统的兼容性
- 与当前 AnyClaw 版本的兼容性

### 5. 缺少完整发布后台

当前发布主要依赖 API 和脚本。

后续需要做一个 Web 管理后台，支持：

- 上传 agent / skill / cli 包
- 填写名称、简介、详情
- 设置标签和 hit signals
- 设置权限
- 设置风险等级
- 设置信任等级
- 管理版本
- 查看下载数据
- 查看安装统计
- 下架 artifact
- quarantine / unquarantine
- 审核发布
- 管理 publisher token

### 6. 官网还没完整产品化

官网目前已经有读取 registry 数据的基础入口，但距离完整官网还需要补：

- AnyClaw 产品首页
- 一键下载入口
- Windows / macOS / Linux 下载区
- 云端市场公开展示页
- Agent / Skill / CLI 详情页
- 安装指引
- 文档入口
- 更新日志
- FAQ
- 联系方式或社区入口

### 7. 安装后自动集成体验还需增强

当前安装器能把包下载、校验、解压、写 receipt。

但不同 artifact 类型安装后如何被 AnyClaw runtime 完整识别，还需要继续增强。

后续应保证：

- skill 安装后自动进入 skill catalog
- agent 安装后能生成或注册 agent profile
- cli 安装后能注册可执行入口
- binding 后 runtime 立即可用
- 卸载后 runtime 清理干净

### 8. 安全体系还需生产级增强

当前已经有基础：

- risk level
- trust level
- permissions
- checksum
- audit
- quarantine

后续建议增加：

- 包签名验证
- 发布者实名或组织认证
- 恶意文件扫描
- 权限 diff 审核
- 安装前风险解释
- 下载链路防篡改
- 沙箱运行
- 高危权限强制二次确认
- artifact 下架后的客户端提示

### 9. registry 存储架构偏轻量

当前 registry 默认使用 SQLite + 本地文件存储。

小规模测试够用，但生产建议逐步升级：

- PostgreSQL 或 MySQL
- 对象存储 OSS / COS / S3
- CDN
- HTTPS
- Nginx 或 Caddy 反向代理
- 日志采集
- 监控告警
- 定时备份

### 10. 分页和大规模市场体验还没完善

后端支持 `limit/offset`，但 UI 当前固定拉取 `limit=100`。

市场条目变多后需要：

- 分页
- 无限滚动
- 分类页
- 搜索防抖
- 本地缓存
- 空状态优化
- 加载骨架屏

## 当前是否可以进入服务器部署

可以进入服务器部署阶段，但建议定位为“测试环境 / 预生产环境”，而不是马上作为正式商业市场上线。

推荐下一阶段目标：

```text
部署 registry + 官网测试环境
-> 配置 AnyClaw 客户端连接服务器
-> 发布 3 个真实 artifact 示例
-> 验证浏览、安装、绑定、升级、卸载
-> 补齐官网和发布后台
-> 增强搜索和安全体系
```

## 推荐后续推进路线

### 第一阶段：服务器基础部署

目标：让云端 registry 真正在服务器上跑起来。

任务：

- 安装系统依赖
- 编译或上传 `anyclaw-registry`
- 配置数据目录
- 配置 admin token
- 配置 systemd 服务
- 配置防火墙
- 配置 Nginx 或 Caddy 反向代理
- 配置 HTTPS
- 跑 registry smoke test

验收标准：

```text
GET /v1/health 返回 ok
GET /v1/artifacts 能返回列表
AnyClaw 客户端能连接 registry
```

### 第二阶段：发布真实市场条目

目标：发布真实 agent / skill / cli 到云端。

任务：

- 整理 artifact 包格式
- 编写 `anyclaw.artifact.json`
- 打包 zip
- 创建 publisher token
- 发布 artifact
- 验证版本列表和下载

验收标准：

```text
云端市场 UI 能看到真实条目
artifact detail 正常
versions 正常
download 正常
```

### 第三阶段：客户端完整闭环验证

目标：验证 AnyClaw 从云端安装后能本地使用。

任务：

- 配置 `marketplace.registry_endpoint`
- UI 切换到 Cloud
- 搜索 agent / skill
- 安装 artifact
- 绑定到 main_agent 或 workspace
- 验证 hot reload
- 验证卸载
- 验证升级

验收标准：

```text
浏览 -> 安装 -> 绑定 -> 使用 -> 升级 -> 卸载 全流程可跑通
```

### 第四阶段：官网产品化

目标：完成 AnyClaw 官网基础版。

任务：

- 官网首页
- 一键下载区
- 市场列表页
- 市场详情页
- 文档入口
- 安装说明
- 下载统计或版本展示

验收标准：

```text
用户打开官网能理解 AnyClaw 是什么
能下载 AnyClaw
能看到云端市场有哪些 agent / skill
```

### 第五阶段：发布后台

目标：让市场可以运营。

任务：

- 登录保护
- artifact 上传
- 元数据编辑
- 版本管理
- 发布者管理
- token 管理
- quarantine 管理
- 下载数据展示
- 审计日志展示

验收标准：

```text
不靠命令行也能发布和管理市场条目
```

### 第六阶段：智能搜索和能力补全

目标：让 AnyClaw 真正像“会自己找能力”一样工作。

任务：

- 建立能力索引
- 扩展 hit signals
- 增加 embedding 搜索
- 增加综合评分
- 完善 Agent 自动搜索提示
- 安装前解释候选能力
- 安装后自动绑定和立即使用

验收标准：

```text
用户表达能力缺口后，AnyClaw 能主动找到合适的云端 skill/agent，并给出合理安装建议
```

## 当前最重要的下一步

建议优先进入服务器测试部署。

原因：

- 本地核心闭环已经完成
- 继续闭门开发容易错过真实部署问题
- registry、官网、AnyClaw 客户端需要在真实网络环境中联调
- 服务器部署后才能真正验证下载、反向代理、HTTPS、客户端配置、官网读取等问题

推荐下一步执行顺序：

```text
1. 部署 anyclaw-registry 到服务器
2. 配置 HTTPS 访问
3. 配置 AnyClaw 客户端 registry_endpoint
4. 发布测试 agent / skill / cli
5. 在 UI 中完成安装和绑定验证
6. 再继续做官网和发布后台
```
